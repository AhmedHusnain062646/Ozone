# Decisions

- argon2 library: `argon2` (node-argon2, argon2id default). Session store: `connect-pg-simple` with `express-session`.
- Postgres host port 5433 (another local Postgres uses 55432; 5432 left free for the user's own).
- Commission stored as integer basis points (850 = 8.5%); DB CHECK 100..5000 enforces the 1%..50% rule. `splitCommission` rounds half up; net is the remainder so gross = commission + net always holds (also a DB CHECK on sub_orders and ledger_entries).
- Ledger append-only is enforced by a Postgres trigger. The single permitted UPDATE is status `pending -> settled` (COD entries settle on DELIVERED); every other column is immutable and DELETE is rejected. Tests TRUNCATE (bypasses row triggers) between cases.
- Seed normalisation: prototype sub-orders carried a $65 shipping line and commission computed on the shipping-inclusive total (e.g. 81.18). Checkout ships at 0 and commission is on item subtotal, so seeded numbers were recomputed (890.00 -> commission 75.65, net 814.35). Mock "disbursed" sale credits became `settled`; the mock $14,200 payout exceeded Atelier Vane's balance, so it is seeded as $1,500.00 (balance would otherwise go negative, violating the payout rule).
- Seed has two buyers (Julian Sterling, M. Dupont) because the prototype had two buyers owning orders; the Dupont return request feeds the admin return queue. Seeded reviews use throwaway `reviewerN@ozone.test` accounts only to satisfy the buyer FK; the "verified purchase" rule is enforced at the API (M4), not retroactively on seed data.
- Seeded product images that pointed at `/src/assets/images/*` are copied to `public/seed-images/` and referenced as `/seed-images/*` so they survive a production build. Remote hotlinks stay as-is (fallback placeholder in the UI, M3).
- helmet CSP `img-src` widened to `'self' data: https:` because product images can be remote https URLs.
- Seed refuses any database whose name does not end in `_dev` or `_test`; re-seeding needs `--reset`. Test global setup applies the same `_test` guard before migrating.
- Environment note: port 3000 is occupied on this machine by an unrelated `gowa` process; Vite falls back to the next free port. Playwright (M10) will start its own servers on dedicated ports rather than assume 3000.
- `drizzle-kit generate` produced 0000_init; 0001_hardening is a hand-written custom migration (trigger + session table) because the schema DSL cannot express either.
- Auth: sessions hold only `userId`; role and seller id are re-read from the DB on every request (`attachAuth`), so a role change or a deleted user takes effect immediately. Cost: one indexed query per request.
- Public `/api/auth/register` can only create buyers; body schemas are `strictObject`, so a forged `role`/`sellerId` is a 400 rather than silently dropped. Seller creation goes through the "apply" flow (M8) and admin approval.
- Login and register both call `session.regenerate` (new sid, old session destroyed). Wrong password and unknown email return the identical 401, and unknown email burns an argon2 verify to equalise timing.
- Origin check: mutating `/api` requests with an `Origin` header must match the request `Host`; requests with no `Origin` (curl, supertest, server-to-server) pass, since cookie auth plus SameSite=Lax already covers legacy browsers. Revisit if a separate web origin is ever introduced.
- Rate limiter uses express-rate-limit's in-memory store: correct for one process, not shared across replicas. `trust proxy` defaults to 0 (env `TRUST_PROXY`), because a fixed hop count lets a direct client spoof X-Forwarded-For and dodge the limiter. Set `TRUST_PROXY=1` behind one reverse proxy; required for Secure cookies to be issued there.
- argon2id params: m=19456 KiB, t=2, p=1 (OWASP minimum); reduced to m=1024 only when NODE_ENV=test.
- Frontend routing: react-router v8 data mode (`createBrowserRouter` from `react-router`, `RouterProvider` from `react-router/dom`, confirmed in node_modules docs). Modal screens (sign-in, product detail, cart, checkout) are child routes of `/` so they deep-link and the Back button closes them. Existing prototype component files are rewritten in place at the same paths (no deletions of files I did not create).
- Identity cache: `me` is set explicitly and every other query is `resetQueries`-ed on login/register/logout. `qc.clear()` was tried first and broke the UI (it orphans mounted observers).
- Gold text colour: brand gold `#C9A25D` fails AA on white (~2.3:1), so text uses `gold-ink` `#78591B` (design doc `secondary`); brand gold stays for borders/fills.
- `?next=` after sign-in only honours same-origin absolute paths (no `//`, no backslash) to avoid an open redirect.
- e2e infrastructure: Playwright starts its own API (4100, NODE_ENV=test, `_test` DB) and Vite (3100) with `API_PROXY_TARGET`; global setup runs migrate + `seed --reset` on the `_test` DB with a fixed local password. Vitest and Playwright share that DB, so run them one after the other (npm scripts do not run them in parallel).
- `.gitignore` gained `test-results/`, `playwright-report/`, `uploads/` (outside the listed scope, needed for the clean-tree criterion).
- Catalog visibility: a product is public only if `is_published` AND its seller is `active`; the predicate lives in one place (`repositories/catalog.ts`). Search escapes `%`, `_`, `\` so they match literally. Price filters/sort use the "from" price (base + cheapest variant delta).
- Review eligibility is literal: the buyer owns a sub-order containing the product whose status is currently `DELIVERED`. A later return/refund therefore removes eligibility for a not-yet-written review; an already-written review stays. `verifiedPurchase` on each review is computed the same way (seeded reviewers have no purchases and show unverified, which is honest).
- Wishlist PUT/DELETE are idempotent (204 both ways). Wishlist and review identity come from the session.
- Drizzle renders column refs without the table prefix in single-table selects; correlated subqueries in such selects must qualify by hand (found via a 500 on /categories).
- The error handler logs 500s through pino, which is silent under NODE_ENV=test; set LOG_LEVEL temporarily or add a throw-to-print probe when a test shows a bare 500.
- Reservations: `reserveStock` is one conditional UPDATE (`stock - reserved >= qty`); zero rows = 409 INVENTORY_CONFLICT. All cart writes lock in the order variant row -> cart line, so add/patch/remove cannot deadlock each other. A cart line IS the hold (`cart_items.expires_at`); invariant: `variants.reserved` = sum of live line quantities (asserted by a mixed-storm test).
- Expiry: `releaseExpired` is a single CTE statement (delete expired lines, decrement `reserved` by the per-variant sum). It runs lazily before every availability read (catalog list/detail, wishlist, cart) and in a 30 s sweeper (`startReservationSweeper`, unref'd, skips overlapping runs). Concurrent runs cannot double-release because the second blocks on the deleted rows' locks and finds nothing. Residual risk: two concurrent release statements touching the same variants in different orders could deadlock in theory; the sweeper is single per process and the loser would simply retry on the next read.
- Adding to a line extends that line's hold to a fresh 10 minutes (as in the prototype); lowering a quantity does not extend it. A user can therefore re-add to keep a hold alive; acceptable for this scope, revisit with per-user hold caps if abuse matters.
- Per-request quantity is capped at 10 (zod) to keep carts sane; stock still bounds the total.
- Cart prices are computed server-side from base price + variant delta; the client countdown uses the server's `serverTime` to correct clock skew.
- Checkout concurrency: a `pg_advisory_xact_lock(hash(buyer:key))` serialises duplicate submissions; inside the lock the order is re-looked-up, so the loser replays the winner's order. Without it the loser blocked on the cart lock, found an empty cart and returned CART_EMPTY (mutation-verified). Locks are taken variants (sorted) then cart lines, matching the cart write paths.
- Idempotency: key is a body field (8-128 chars) scoped per buyer by a unique index; replay returns 200 + `Idempotent-Replay: true`; same key with a different payment method or address returns 422 IDEMPOTENCY_KEY_REUSED.
- Payments: `PaymentProvider` interface with a simulated gateway. The checkout body is a strict schema, so card numbers, prices and totals are rejected with 400. The only test control is `sandboxOutcome: approve|decline` on the sandbox card. Gateway runs inside the transaction (fine for an in-process simulator; a real gateway would authorise first and use the idempotency key on its side).
- Ledger at checkout: one `sale_credit` per sub-order (gross = subtotal, commission, net); `settled` for card/escrow, `pending` for COD (settles at DELIVERED in M7). Buyer DTOs omit commission/net; admins see them.
- Status events use JS-side timestamps (PLACED, then PAID +1 ms) because `now()` is constant within a transaction and would make history order ambiguous.
- Operational note: a Playwright run left alive by an interrupted command shares the `_test` database with the next run and causes spurious failures; check `pgrep -fl playwright` before re-running.

## M7 order lifecycle
- One graph: `server/domain/order-state.ts` (`ALLOWED_TRANSITIONS`, `isLegalTransition`, `authorizeTransition`), pure and unit-tested. Check order in the service: ownership (403) -> legality (409 ILLEGAL_TRANSITION) -> role permission (403) -> body rules (400 TRACKING_REQUIRED / REASON_REQUIRED). Legality comes before role so a wrong-state request is a 409 for everyone who owns the parcel.
- Return approval and refund are not on the generic endpoint: `POST /api/sub-orders/:code/return-decision` is admin-only; approve runs RETURN_REQUESTED -> RETURNED -> REFUNDED in one transaction (two status events, 1 ms apart, actor = admin), restocks and appends a `refund_debit` that is the exact negation of the sale credit. Reject returns to DELIVERED with no money or stock change.
- PLACED -> PAID is only accepted for cash-on-delivery orders (seller confirms); card/escrow orders are PAID by the gateway at checkout.
- Concurrency: every command locks the sub-order row (`FOR UPDATE`) and re-reads status in the transaction. Mutation-verified: without the lock, 5 concurrent cancels double-restock.
- Ledger stays append-only: a cancel/refund never edits the sale credit; it adds `refund_debit` (settled if the sale was settled, pending for unsettled COD). COD sale credits flip pending -> settled (the one update the trigger permits) at DELIVERED. Parent payment status becomes REFUNDED only when every parcel is cancelled/refunded, and PAID for COD once no parcel is still open.

## M8 seller console
- Seller application: `POST /api/auth/apply-seller` (strict body, rate-limited like register) creates user(role=seller) + atelier(status=pending_approval, verified=false) in one transaction at the platform default commission (`settings.default_commission_bps`, falling back to 850). Status/commission fields in the body are a 400. Only an admin changes status (M9).
- Seller API is scoped by the session's `sellerId`; ownership is part of each WHERE, so another seller's product/variant/image is a 404 (not 403) and nothing changes.
- Publish gate: unpublishing is always allowed; publishing and payouts need `status = active` (403 SELLER_NOT_ACTIVE). Drafts, stock and reading balances work while pending.
- Stock floor: `PATCH /seller/variants/:id` runs `releaseExpired` then locks the variant row and rejects `stock < reserved` with 409 STOCK_BELOW_RESERVED.
- Images: `ImageStorage` interface + local-disk implementation (`UPLOAD_DIR`, default `./uploads`, OS temp dir under test). Multer memory storage, 2 MB cap (413), type decided by magic bytes (PNG/JPEG/WebP only; SVG/HTML with a spoofed content type is 415), max 8 per product, files named by UUID. `/uploads` is served statically (helmet nosniff), unknown files 404. Deleting only removes files under /uploads (seeded/remote URLs are not ours).
- Balance = settled net (sale credits and refund debits) + payout rows (negative); pending (COD) is reported separately and is not withdrawable. Payouts lock the seller row, so concurrent requests cannot both spend the same balance (mutation-verified).
- CSV is a real server-side download (`/api/seller/ledger.csv`, attachment, only own rows); string cells starting with = + - @ get a leading apostrophe against spreadsheet formula injection.
- New dependency: none (multer was already on the approved list in package.json).
